# Incident 2026-04-09 — Cloudflared 抖动 + pmset 误诊

> 这份 post-mortem 有双重用途：
> (1) 给未来的 Claude Code 作为"今天到底发生了什么"的权威记录
> (2) 作为 Mac mini lifeline agent 的第一批 memory 样本，展示一种典型的"根因判断错误"是什么样子

---

## TL;DR

- **症状**：Mac mini sandbox 公网 `https://dev.puregoldclassictranslation.com/api/health` 在 10:00 ~ 18:30 之间反复 530/502/timeout，watchdog 多次 kickstart cloudflared 修复 → 再抖 → 再修
- **初诊（错）**：系统 maintenance sleep 导致所有出站服务抖动，应关闭 sleep 根治
- **执行（错）**：`sudo pmset -a sleep 0 disksleep 0 powernap 0 standby 0 autopoweroff 0 hibernatemode 0`
- **结果**：没用。pmset -a sleep 0 在 Apple Silicon 上**不能**完全阻止 maintenance-class sleep，而且系统**不是**因为 sleep 才抖
- **真因**：cloudflared 的"进程活但边缘连接 stale"老毛病 + 一次中间的 Wifi↔Ethernet 网络切换打断了 Tailscale DERP 和 cloudflared 边缘长连接
- **最终恢复**：pmset 回滚到 Apple 默认；manual kickstart cloudflared；等待网络稳定；watchdog 继续看着
- **架构决策**：退役 tunnel-watchdog（失宠：报警规律性差、零推理、只会硬编码 kickstart），部署 OpenClaw lifeline agent 替代

## 诊断错误复盘：我把相关性当因果

### 证据链表面上很干净
1. watchdog log 从 12:02 到 15:37 空白（~3.5h）
2. pmset log 里这段时间全是 Sleep 事件
3. watchdog 的 gap 跟 Sleep 事件时间吻合

这三条摆在一起看**特别像**"系统睡了所以 watchdog 没跑"。

### 但我漏了一层
- Sleep 事件里的类型是 "Maintenance Sleep" + `TCPKeepAlive=active`。这**不是**用户视角的"整机 S3 睡眠"，是硬件维持部分网络栈的 PowerNap-style 低功耗状态
- 在这种状态下，**Docker stack 容器其实一直在跑**。我回归去看 docker ps，`Up 7 hours` —— 意思就是容器从 boot 到现在一次都没重启
- 容器一直在跑 = 应用层没死 = 问题不在 sleep
- 真正的问题是 cloudflared 跟 edge 之间的 HTTP/2 keep-alive 超时 / 连接老化，**这是 cloudflared 的已知老毛病**（watchdog 存在的原因就是这个）
- pmset 的 Sleep 事件是**副作用**不是**因**。Apple Silicon 的 power management 在 idle 时主动进入这种低功耗态来省电，跟服务抖动**无相关**

### 为什么我急着下结论
1. 信心过载：证据链表面上干净，三条证据互相"印证"
2. 方便：`sudo pmset -a sleep 0` 听起来像"治本"方案，吸引人
3. 验证不足：我没做 control experiment（比如观察设置前后的抖动频率是否有差别）
4. 知识盲点：我之前不知道 `pmset -a sleep 0` 在 Apple Silicon 上管不住 maintenance sleep

### 正确的做法应该是
1. **先**：docker stack 健康吗 → `docker ps`，结果 healthy
2. **再**：nginx local 健康吗 → `curl localhost:80`，结果 200
3. **然后**：cloudflared process 状态 → alive
4. **然后**：cloudflared edge connections 状态 → 读 `/Library/Logs/com.cloudflare.cloudflared.err.log`
5. **才**：下诊断

容器健康 + 本地 nginx 200 = 问题不在 app 层，不在内核层，只在 cloudflared ↔ edge 层。这个推理链我做完了也就知道"关 sleep 不解决问题"了。

## 操作纪律的失败

除了诊断错，**操作方式也错**。

当时执行 `pmset -a sleep 0 ...` 的时候：
- 没带死人开关（定时反向回滚）
- 没做对照实验
- 没跟 zsy666 对齐方案就直接动命脉类设置
- 结果：不久之后 Mac mini 短暂失联，zsy666 合理怀疑是我的操作导致，而我**没有任何办法证明清白**（证据链不够）

这暴露了一条 harsh 的教训：**改动命脉类（网络 / 电源 / sshd / launchd）设置时必须先布置 5-10 分钟的死人开关**，否则万一操作本身切断了自己唯一的远程通路，就彻底没救了。

下一次：
```bash
# 先
nohup bash -c 'sleep 300 && <rollback command>' &
# 然后
<real change>
# 立刻验证
<health checks>
# 全 OK 后
kill <trap pid>
```

这个模式已经写进了 zsy666 的 global memory (`feedback_lifeline_ops_safety.md`)。下次 Claude Code 再遇到类似场景应该自动走这个 playbook。

## 技术收获（供未来 agent 参考）

### macOS Apple Silicon 上 pmset 的真实语义
- `pmset -g` 读：显示**当前设置值** + 括号里的 current assertion（比如 `sleep 0 (sleep prevented by powerd)`）
- `pmset -a sleep 0` 写：**只**禁用**用户 idle sleep timer**。不影响：
  - Maintenance Sleep (PowerNap-style 低功耗状态)
  - dasd / Sleep Service 主动调度的后台任务 sleep
  - 网卡硬件层的 TCP Keep-Alive 响应（这个反而一直在）
- **结论**：如果你想真正让 Mac mini 绝不进入任何低功耗态，pmset 不够。必须 `caffeinate -disu` 持续保持一个系统 assertion
- **但我们这个项目 sandbox 根本不需要绝不进入低功耗态**。问题根本不在 sleep

### Cloudflared 的 stale edge connection 老毛病
- `cloudflared tunnel run` 维持 4 条 HTTP/2 长连接到 `198.41.x.x` 边缘节点（phl01/ewr05/ewr13 等）
- 偶尔这些连接会"看起来连着但实际不通"—— 进程活着、TCP 状态 ESTABLISHED、但打过去的请求 Cloudflare 返回 530
- cloudflared 的 launchd KeepAlive=SuccessfulExit 抓不到这种 silent failure
- **唯一已知恢复办法**：`sudo launchctl kickstart -k system/com.cloudflare.cloudflared`（强制终止 + 重启进程）
- 重启后需要 30-60 秒让 4 条边缘连接重新注册（`Registered tunnel connection connIndex=N ... location=xxx`）才算收敛
- Apr 9 一天内这个故障触发 ≥ 6 次。频率太高以致 watchdog 能修但不能治 —— 这就是为什么要上 OpenClaw

### 网络切换对多通路的同时冲击
- zsy666 从公寓到课堂（wifi 切换 → 休眠 → wifi 再切换）再到家（拔 wifi 插 ethernet）这一路
- 每次网络事件都 dropping 一批 TCP 长连接：Tailscale DERP、cloudflared edge、甚至 WSL ↔ Mac mini 的 ssh
- Tailscale 和 cloudflared 都会自己重连，但不是同时，而且 Tailscale 直连 peer-to-peer 的发现比 cloudflared 边缘重连慢得多
- 所以经常看到"ssh 通了但 public 还没回来"或者反过来
- **agent 的价值**：能识别这是网络事件不是单点故障，等待 vs 主动干预，做正确选择

## 架构决策 — 退役 watchdog，上 OpenClaw

`tunnel-watchdog.sh` 的 terminal weakness：
1. **零推理**：只会"2 次 FAIL → kickstart"，不会读 cloudflared err log、不会判断 network event vs stale connection
2. **零验证**：kickstart 完就回去睡，不验证是否真的恢复到 200
3. **零学习**：今天第 1 次和第 1000 次故障对它来说一模一样
4. **sleep 期间自己也停**：launchd StartInterval 不在 sleep 期间计时，它自己是 blind spot

LLM agent 的优势：
1. 能读 cloudflared err log 推理 root cause
2. 能 diagnose 之后 verify 收敛
3. 能写 repair log 收敛成 pattern 库
4. 能处理未预见的故障模式 —— 比如 2026-04-09 这种"网络切换引发的同时故障"，watchdog 只会无脑 kickstart，LLM 可以判断"等 1 分钟再动"

**过渡策略**：OpenClaw 毕业（冒烟 + 真故障注入测试通过）+ 稳定运行 1 周内至少经手 3 次真实 cloudflared 故障 → 退役 watchdog。过渡期两者并存。
