# v4 论坛 — 实施计划

> 状态：**实施中，第 1 至 5 部分已完成本地实现与验证，尚未部署到远端**。初稿为 2026-09-18，最近更新于 2026-09-19。实际进度见 [v4-changelog.md](v4-changelog.md)。
> 本轮依据用户确认：admin 是无志愿者身份的系统管理员，拥有论坛最高权限；其他账号等级不作用于论坛；圈务角色独立；账号注销保留发言；圈子可归档隐藏；增加消息中心和个人论坛管理入口。
> 本文记录完整目标设计；各部分实际交付与验证以 v4 changelog 为准。

社区功能：圈子 → 帖子 → 平铺评论，带点赞、收藏、置顶、精华、站内消息。

## 1. 产品决策

| 议题 | 决定 |
|---|---|
| 系统管理员 | `Account.role = admin`，不需要 Volunteer，拥有全站论坛管理及普通参与能力 |
| 普通账号等级 | `user / a_admin / b_admin` 在论坛中的基础权限一致；部门、台账、录入权限不参与论坛授权 |
| 圈务角色 | **圈主 / 协管员**；都是按圈子授予的身份，一个人在不同圈子可以有不同身份 |
| 建圈 | 系统管理员建圈并指定圈主；保留多圈主能力。先只建新人圈 `newcomers` |
| 圈务任命 | 系统管理员任免任意圈务角色；圈主任免本圈协管员，可把自己的圈主身份转让给另一有效账号 |
| 普通参与 | 所有有效登录账号均可浏览、发帖、评论、点赞、收藏，不需要加入圈子才能参与 |
| 关注圈子 | 提供关注/取消关注；只影响个人入口，不赋予管理权限，不自动订阅所有新帖通知 |
| 可见性 | 论坛正文与附件均登录可见；归档及删除内容另受状态和权限约束 |
| 编辑 | 作者编辑自己的内容；系统管理员可编辑任何内容并留下明确的管理编辑标记与审计；圈主/协管员不改写他人正文 |
| 删除 | 帖子与评论软删除；正常产品流程不硬删论坛内容 |
| 账号注销 | 历史帖子、评论保留，作者显示“已注销”，不显示原姓名、头像或个人资料链接 |
| 圈子归档 | 系统管理员归档/恢复；归档隐藏整圈、停止互动，数据保留 |
| 排序 | 热门默认，另提供“最新回复”“最新发布”；置顶独立，精华提供筛选入口 |
| 消息 | 顶部信封图标进入“消息中心”，一期接入回复和圈务通知；未来可承接其他业务通知 |
| 个人中心 | 每个账号都有“我的帖子 / 我的评论 / 我的收藏 / 我的圈子”，包括没有志愿者档案的 admin |
| 内容编辑器 | Markdown + 简单工具条 + 常用 Emoji 面板；一期不渲染图片，不做楼中楼或所见即所得编辑器 |

## 2. 分期与交付顺序

一期分六部分实施：

| 部分 | 做什么 | 完成后能验证什么 |
|---|---|---|
| 1. 数据与身份基础 | 数据库迁移、账户关联、论坛权限入口、注销保留发言、审计类型 | 无志愿者身份的 admin 能参与；注销不丢讨论；现有台账不受影响 |
| 2. 圈子与圈务 | 新人圈初始化、建圈、圈主/协管员任免、转让、归档恢复、圈子管理页面 | 各角色权限正确，不能跨圈管理；归档隐藏和恢复完整 |
| 3. 发帖与评论 | 帖子列表和详情、Markdown 编辑预览、Emoji、平铺评论、编辑删除、个人中心的帖子和评论 | 能完成“发帖 → 回帖 → 修改 → 找回原讨论”的完整流程 |
| 4. 互动与内容发现 | 点赞、收藏、关注圈子、置顶、精华、三种排序，补齐个人中心四个入口 | 常用操作顺手；老帖能回流；热门排序可用具体样例解释 |
| 5. 消息中心 | 顶部信封、未读数、回复与圈务通知、已读操作、评论定位 | 别人回复后能收到提醒，点击准确回到对应评论 |
| 6. 整体验收与交付 | 权限回归、迁移验证、并发和删除边界、手机体验、端到端测试、更新文档 | 得到一个可以交给用户集中测试的一期版本 |

二期：图片上传、压缩、私有文件读取、粘贴上传、存储配额、数据库和文件备份及恢复演练。

三期：@提及、举报、搜索、更多业务通知；按真实需求排期。

现有头像已支持客户端压缩后以 data URL 存入 `Volunteer.avatar`，外部 URL 只是默认头像。二期可以统一文件基础设施，头像迁移另列任务。

## 3. 数据模型与身份生命周期

### 3.1 身份选择

**论坛行为关联 Account。** Volunteer 仅用于在账号仍存在时补充展示资料，论坛不新增强依赖 Volunteer 的外键。系统管理员用 `Account.name` 和默认管理头像参与。

以下是模型契约，不是可直接粘贴的 Prisma schema。实施时补全 Account 的反向关系、命名关系与审计枚举，再生成和验证真实 migration。

| 模型 | 关键字段与约束 |
|---|---|
| Circle | `id, slug(unique), name, description, status(ACTIVE/ARCHIVED), createdById?, archivedAt?, createdAt, updatedAt`；createdBy → Account，SetNull |
| CircleRoleAssignment | `id, circleId, accountId, role(OWNER/STEWARD), addedAt`；unique(circleId, accountId)，index(accountId)；账号删除 Cascade 授权行 |
| CircleFollow | `circleId, accountId, createdAt`；复合主键；账号删除 Cascade 个人关注 |
| Post | `id, circleId, authorId?, title, body, status(ACTIVE/DELETED), isPinned, pinnedAt?, isFeatured, featuredAt?, lastActivityAt, editedAt?, lastEditKind?(AUTHOR/ADMIN), deletedAt?, createdAt, updatedAt`；author → Account，SetNull |
| PostComment | `id, postId, authorId?, body, status(ACTIVE/DELETED), editedAt?, lastEditKind?(AUTHOR/ADMIN), deletedAt?, createdAt, updatedAt`；author → Account，SetNull |
| PostLike | `id, postId, accountId?, createdAt`；unique(postId, accountId)，account → Account，SetNull；保留注销者点赞，但不公开点赞者名单 |
| PostFavorite | `postId, accountId, createdAt`；复合主键；account → Account，Cascade |
| Notification | `id, recipientId, actorId?, type, eventKey, targetType, targetId, postId?, circleId?, readAt?, createdAt`；recipient → Account，Cascade；actor → Account，SetNull；unique(recipientId, eventKey) |

所有帖子、评论、点赞、收藏都必须定义真实关系及反向关系，不能只声明 `postId`。Circle、Post 的内容外键采用 Restrict，防止硬删父对象意外丢失讨论；软删与归档不触发级联。

建议索引：Post(circleId, status, isPinned, lastActivityAt)、Post(authorId, createdAt)、PostComment(postId, status, createdAt)、PostComment(authorId, createdAt)、PostLike(postId, createdAt)、PostFavorite(accountId, createdAt)、Notification(recipientId, readAt, createdAt)。

PostLike 使用独立主键及可空账号外键：账号注销后既能留住历史点赞，也不会把多个注销者合并成一条。近期热度仅计入仍关联账号的互动；展示总点赞数保留历史值。取消点赞删除自己的行，重新点赞视作新事件，不发送点赞通知。

### 3.2 账号删除

- `authorId = null` 是已注销显示的唯一判断，不用旧姓名快照重新识别作者；新建同邮箱账号也不能继承旧发言。
- 帖子和评论内容、顺序、编辑标记保留；可空的创建者、通知操作者外键 SetNull。
- 圈务任命、关注、收藏、收件箱随账号删除；其他人的回复提醒保留，操作者显示“已注销”。
- 注销最后一位圈主不阻塞注销。圈子进入“待指派圈主”的管理视图，系统管理员兜底；协管员不会自动升级。
- 本次不绕过现有台账/标签数据导致的账号删除限制：**只有原有删除事务整体成功**，才应用上述论坛注销结果；失败必须整体回滚。
- 系统管理员最高权限适用于论坛能力；现有禁止删除最后一个有效系统管理员等账户级约束继续保留。
- 适配 `AccountService.deleteAccount`、`AdminService.resetToSystemAdmin`。显式全系统重置按外键顺序清理论坛数据，与日常账号注销分别测试。

### 3.3 计数与迁移

展示评论数只统计 ACTIVE 评论；点赞数从实际行聚合，收藏数和名单不向其他人公开。近期不同评论人数通过聚合计算，不能拿评论总数替代。

`lastActivityAt = max(帖子创建时间, ACTIVE 评论的创建时间)`；评论创建/删除/恢复与该值更新同事务。并发修改同帖必须串行化或采用可重试的 Serializable 事务，避免旧请求把时间覆盖回去。编辑、点赞、收藏、管理操作不刷新“最新回复”。

迁移以新增表为主，但需修改 Account 关系声明并扩展 `AuditAction / AuditTargetType`。已验证旧客户端可读写原有账户/台账，但不能解码新增论坛审计枚举。出现论坛审计数据后，回退应用须保留新版 Prisma Client 及论坛审计访问过滤，不能直接部署未经兼容处理的旧版本。回退保留新增表和已有数据，不删表或删除审计记录。

## 4. 排序：公开策略与本项目规则

### 4.1 参考依据

Discourse 的公开实现将历史热度与近期互动分别衰减，并统计近期不同参与者；这比累计评论数被最后一条回复整体重新激活更适合作为参考。[官方说明](https://meta.discourse.org/t/discover-popular-conversations-in-your-community-with-hot-topic-sorting/296747)、[实现源码](https://github.com/discourse/discourse/blob/main/app/models/topic_hot_score.rb)。

贴吧公开的**话题热议榜**规则提到一定时间段内的发帖、回帖量，并按小时更新；这不是单吧帖子列表排序的完整公式。本轮未找到可核验的单吧热门精确公式，因此不声称复刻贴吧算法。[贴吧榜单规则](https://c.tieba.baidu.com/hottopic/browse/topicList?res_type=1)。

### 4.2 三种排序

| 入口 | 规则 |
|---|---|
| 热门（默认） | 历史热度衰减 + 近期参与热度衰减；精华 ×2 |
| 最新回复 | `lastActivityAt DESC`；从未回复的帖子使用创建时间 |
| 最新发布 | `createdAt DESC`；全部历史可分页 |

置顶在这三种视图中优先，多个置顶按 `pinnedAt DESC, id DESC`。置顶只在本圈起作用。精华是质量标记，可单独筛选；本身不永久置顶。

### 4.3 一期初始公式

下面是**借鉴公开策略的项目自定义公式**，参数为待用户测试的初值，不是贴吧或 Discourse 的原式，也不是已验证的使用结论。

```text
score = featuredMultiplier × (
    (1 + ln(1 + L_all)) / (ageHours + 12)^1.2
    + (L_recent + 2 × U_recent) / (recentAgeHours + 12)^1.2
)

featuredMultiplier = 精华 ? 2 : 1
recentWindow = 7 天
```

- `L_all`：当前保留的全部点赞，包含注销者的历史点赞；对数压缩累计优势。
- `L_recent`：近 7 天的当前有效点赞，排除作者给自己的赞以及已注销账号的赞。
- `U_recent`：近 7 天 ACTIVE 评论的不同作者账号数，排除楼主本人和已注销账号；同一个人发十条只计一个参与者。
- `ageHours`：距发帖的小时数。
- `recentAgeHours`：距窗口内**最早一条符合上述条件的互动**的小时数；无符合条件的互动时近期项为 0。窗口移动时重新计算，不把该时间永久存进 Post。
- 两个年龄都截断到至少 0。单个请求固定同一 `now` 进行窗口筛选、算分、总数和分页。
- 本人补充内容会更新“最新回复”，但不增加近期热门参与人数；历史评论数不会因一次顶帖重新获得全部权重。
- 精华倍数、窗口、权重、offset、gravity 放进一处常量。滚动窗口仍会产生排名变化，取消后重新点赞也可能影响近期项；一期用频控与观察处理，不声称公式能完全防刷。

### 4.4 查询与分页

一期热门读取该圈**全部 ACTIVE 帖子的排序字段**，批量聚合点赞与近期评论作者，应用层算分后分页，再只加载当前页正文摘要及作者资料。禁止逐帖 N+1、全量加载 Markdown/头像或按发布时间截断 90 天导致老帖无法回流。

所有排序使用 id 作最终同分次序。“最新回复/最新发布”走数据库分页；评论使用 `createdAt, id` 稳定游标独立分页。热门每次请求重新排名，一期允许翻页期间因新增互动发生位移，前端去重并提供刷新；需要严格快照时再引入列表快照游标。

不设“2000 条必定失效”的硬阈值。用真实数据观测查询耗时、候选数、内存和 p95；到需要时选择数据库聚合或缓存，而不是预先强制定时重算架构。

## 5. 权限与圈子生命周期

| 动作 | 普通登录账号 | 本圈协管员 | 本圈圈主 | 系统管理员 |
|---|:---:|:---:|:---:|:---:|
| 浏览、发帖、评论、点赞、收藏、关注 | ✓ | ✓ | ✓ | ✓ |
| 编辑/删除自己的内容 | ✓ | ✓ | ✓ | ✓ |
| 编辑他人的帖子/评论 | — | — | — | 全站 |
| 软删/恢复他人内容、置顶、加精 | — | 本圈 | 本圈 | 全站 |
| 修改圈名、简介 | — | — | 本圈 | 全站 |
| 任免协管员 | — | — | 本圈 | 全站 |
| 转让自己的圈主身份 | — | — | 本圈 | 全站 |
| 新增/移除圈主、改 slug | — | — | — | 全站 |
| 建圈、归档、恢复圈子 | — | — | — | 全站 |

- 服务层统一判断 `isSystemAdmin` 与圈务角色；不使用台账的 `isReviewer`、部门范围或 a/b_admin 等级推导圈务权。
- 圈主转让在同一事务里授予接收者 OWNER 并移除转让者该任命；目标必须是有效账号，不允许转给自己。其他圈主不受影响。
- 管理员任免与账号注销等并发情况需要验证，不能用客户端禁用按钮维持角色约束。
- 作者软删后，普通列表、正文直链、评论和收藏不可读；个人中心可显示删除状态与操作时间，不泄露已经不可见的正文。圈务人员的恢复在专用管理视图进行并写审计。
- **归档整圈**：从普通论坛、关注列表中隐藏，互动写操作拒绝；帖子直链只显示“圈子已归档”。个人中心可保留自己的关联条目及状态，不展示被隐藏内容的摘要；允许清理本人的收藏和关注，不改变内容或圈务身份。
- 系统管理员和该圈圈务人员可在专用管理视图查看归档内容；仅系统管理员可恢复圈子。归档期间除系统管理员恢复圈子及调整圈务人员外，内容保持只读。
- 恢复圈子不恢复之前已软删的帖子/评论，也不群发旧回复通知。
- 所有内容修改、互动、通知跳转均重新校验父帖与圈子状态。圈务操作需要同时核对内容所属 circleId，不能拿别圈的权限操作。
- admin 可编辑他人内容，UI 显示“由系统管理员编辑”；管理编辑前后内容进入受限审计，但一期不提供普通帖子版本历史界面。

## 6. 消息中心

### 6.1 入口与一期事件

顶部右侧增加信封图标，名称 **消息中心**，显示未读数（超过 99 显示 99+）；桌面和移动端均可用。点击进入 `/messages`，提供全部/未读、单条已读和全部已读。

一期事件：

- 他人评论我的帖子 → 通知楼主；不给自己回复自己的帖子发通知。
- 被任命/移除圈主或协管员、收到圈主转让 → 通知受影响账号。
- 自己的内容被管理编辑、删除、恢复、置顶/取消置顶、加精/取消加精 → 通知作者，操作者为作者本人时跳过。

一期评论仍平铺，不引入“回复某条评论”的隐含嵌套模型，也不向每个参评者广播后续回复。消息点击定位具体评论；评论不在首屏时由定位接口取得所在页/上下文，不能只拼一个不可见的 DOM 锚点。

“我的评论”支持回到原讨论。针对评论的定向回复提醒以后与 @提及一起扩展。圈子关注不等于全量通知，点赞也不发送逐条通知。

### 6.2 存储与一致性

- Notification 以收件人账号为边界；读取、标记已读、统计未读均在服务端限定 recipientId。
- 内容写入/圈务变更与通知写入同事务。`eventKey` 标识一次实际事件，重试不得重复生成；可重复发生的管理操作用本次审计 ID，回复用新评论 ID。
- 不存帖子正文和评论全文快照；通知文案由类型、当前可见目标及安全字段生成，避免帖子删除后仍从通知读到正文。
- 删除评论后，其回复通知清理；整帖删除或圈子归档后，相关回复通知不再计入未读，也不返回旧标题摘要。管理处置通知仍显示通用结果。
- 用户点击失效目标时显示“内容已删除/圈子已归档”，可完成已读，不能留下清不掉的红点。
- “全部已读”带本次查看的时间截止点，只更新截至该点已收到的通知，避免并发到达的新消息被误标。
- 一期使用当前数据库 + 页面可见时约 60 秒轮询未读数，窗口重新获得焦点时刷新；退出或切换账号清空账号相关缓存。不引入 WebSocket、邮件服务或消息队列。
- 模型保留事件类型和目标定位，日后可增加台账待确认、系统公告等通知；一期不增加点对点私信或站内邮件编辑器。

## 7. 前端与个人中心

路由全部需要登录：

- `/forum`：圈子入口；只有新人圈时优先呈现可参与内容，避免空分类墙。
- `/forum/c/:slug`：帖子列表、三个排序、精华筛选、关注圈子、发帖入口。
- `/forum/p/:id`：正文、编辑与管理操作、独立分页评论、评论定位。
- `/messages`：消息中心。
- `/me/forum?tab=posts|comments|favorites|circles`：统一的个人论坛工作区。
- `/forum/c/:slug/manage`：授权圈务人员的设置、成员任命及内容管理视图。

论坛首页不再单设圈务工作台，进入具体圈子后使用“圈子管理”。已归档圈子在首页折叠展示给有权管理的账号，保留恢复入口。帖子阅读视图统一采用普通成员的操作方式：点赞、收藏、评论及管理本人的发言；管理他人内容、恢复、置顶及加精仅在圈子管理进入的帖子管理视图中展示。

**每个人的个人中心都能进入论坛工作区。** 当前 admin 的 `/me` 渲染 AdminCenter，不能只给 Volunteer 版 MePage 加入口；在两种个人中心复用同一个论坛入口组件。

个人工作区：

| 标签 | 能做什么 |
|---|---|
| 我的帖子 | 按时间浏览自己的帖子、看回复数、进入详情、编辑/删除；已删除或归档关联显示状态 |
| 我的评论 | 看评论及所属帖子、定位上下文、编辑/删除；父内容不可见时不返回摘要 |
| 我的收藏 | 浏览和取消收藏；隐藏目标显示通用不可用状态，仍可移除收藏 |
| 我的圈子 | 查看关注的圈子、担任圈主/协管员的圈子；按实际身份显示进入与管理操作；管理角色移除不偷偷取消用户关注 |

管理组件放 `components/Forum/`，消息组件放 `components/Notifications/`；不要把新表单继续堆进已有的大型 AdminCenter/MePage。系统管理员在论坛首页建圈；设置、归档和内容治理统一在具体圈子的管理页完成。

Markdown 渲染和 Emoji 面板独立封装。帖子列表只渲染纯文本摘要。服务返回与用户权限相符的 `capabilities` 供 UI 显示按钮，写入时仍由服务重新鉴权。

## 8. API 与服务层

论坛统一前缀 `/api/v1/forum`，通知使用可扩展的 `/api/v1/notifications`。所有端点经过 authenticate；论坛写入按账号频控，避免同一办公室共用 IP 时分享一个 30 次/分钟额度。保留外围 IP 防护并验证 Cloudflare/nginx 代理链。

| 方法 | 论坛相对路径 | 说明 |
|---|---|---|
| GET / POST | `/circles` | 浏览有效圈子 / admin 建圈 |
| GET | `/circles/:slug` | 读圈子 |
| PATCH | `/circles/:id` | 圈主改名称简介；admin 还可改 slug |
| POST / DELETE | `/circles/:id/archive` | admin 归档 / 恢复，幂等 |
| GET | `/circles/:id/manage` | 本圈圈务或 admin 的管理资料（包括归档状态） |
| PUT / DELETE | `/circles/:id/stewards/:accountId` | 任命/移除协管员，不允许借此覆盖 OWNER |
| PUT / DELETE | `/circles/:id/owners/:accountId` | admin 任免圈主 |
| POST | `/circles/:id/transfer` | 圈主转让本人身份，admin 可指定来源 |
| PUT / DELETE | `/circles/:id/follow` | 关注/取消关注 |
| GET / POST | `/circles/:slug/posts` | 分页列表（sort=hot/activity/new） / 发帖 |
| GET / PATCH / DELETE | `/posts/:id` | 详情 / 编辑 / 软删 |
| POST | `/posts/:id/restore` | 圈务或 admin 恢复 |
| PUT / DELETE | `/posts/:id/pin`、`/posts/:id/feature` | 圈务或 admin 置顶、加精；幂等 |
| PUT / DELETE | `/posts/:id/like`、`/posts/:id/favorite` | 点赞、收藏；幂等 |
| GET / POST | `/posts/:id/comments` | 评论独立分页（可按 commentId 定位） / 评论 |
| PATCH / DELETE | `/comments/:id` | 编辑 / 软删 |
| POST | `/comments/:id/restore` | 圈务或 admin 恢复 |
| GET | `/me/posts`、`/me/comments`、`/me/favorites`、`/me/circles` | 个人工作区分页数据 |

通知端点：GET `/`（`filter=all|unread`、`page`）、GET `/unread-count`、PATCH `/:id/read`、POST `/read-all`。列表返回 `viewedAt` 和 `unreadCount`，全部已读 body 含查看截止时间 `viewedAt`；服务端校验并限制到当前时间。单条已读响应重新检查目标可见性，返回当前可用的跳转地址或通用不可用状态。

- 新增 CircleService / PostService / NotificationService；controller 只做 HTTP 适配。
- 新增统一论坛权限与可见性 helper。普通查询默认要求 ACTIVE 父圈/父帖；管理查询显式授权，不使用任意 `includeDeleted=true` 绕过。
- DTO 白名单：authorId、圈务角色、计数、status 等不接受普通发帖/编辑请求直接赋值。
- 字段上限：标题 100、正文 5000、评论 1000 个 Unicode 码点，trim 后非空；前后端口径一致。圈名 40、简介 500；slug 小写字母/数字/连字符，最大 64，禁止开头结尾连字符。
- 分页默认 20、最大 100；复用 QueryUtils 的参数校验，注意它返回 limit 而非 Prisma take。普通列表沿用 `{ success, count, total, totalPages, currentPage, data }`；评论额外返回 nextCursor/定位信息。
- 实际发生的圈务变更和 admin 改他人内容在同事务写 AuditLog，扩展论坛 target/action；普通发帖评论不写全局审计，通知也不是审计替代品。
- 置顶、加精、点赞、收藏、关注及已读操作保持幂等；重复请求不重复通知、不刷新无变化的置顶时间。
- 首个新人圈按 slug 幂等初始化；不依赖重新执行会影响现有组织配置的全量 seed，不凭空创建志愿者或替身 admin。

## 9. 内容与附件边界

一期：数据库只存 Markdown 原文；`markdown-it` 关闭原始 HTML 并禁用图片渲染，再经 `DOMPurify` 白名单清洗。链接按允许协议校验，禁 javascript/data 等主动内容；强制 `rel="noopener noreferrer"`。预览和详情复用同一渲染器，评论同样处理。不向未授权访问返回作者私人资料、正文或通知摘要。

二期：

- 有鉴权的上传接口；限制单图 10 MB、单帖 9 张，同时限制请求大小、总像素和解码并发。
- 按文件头验证后用 sharp 实际解码、压到最长边 1600px WebP、剥 EXIF；校验失败拒绝，生成随机文件名。
- Mac 本地持久 volume 存储。附件模型关联 uploaderAccountId、所属帖子、大小、mime、状态；校验上传者与挂载目标，处理未发布附件及孤儿文件清理。
- **不公开静态目录。** 使用携带现有 Bearer token 的 API 获取文件并通过前端 blob URL 展示，或以后改为经过鉴权的内部文件转发；不能假设 img 标签会自动发送 Authorization。
- 每次读取检查登录及父圈/帖子状态，私有缓存策略；归档、软删后拒绝后续读取。已合法下载到客户端的文件不能承诺远程撤回。
- 改造 `pg-backup.sh`、离机复制和 `pg-restore.sh`：备份数据库与文件清单，定义一致的备份时间边界和文件保留策略，校验恢复后附件完整性。只备份成功不算验收，必须实际恢复演练。
- 部署前实测容量、备份空间、镜像和依赖风险；不沿用初稿的 121 GB / 109 个漏洞等未重新核验数值作为当前事实。
