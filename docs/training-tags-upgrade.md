## 使用入口

- **培训考勤 `/training`**：管理员、全局录入员及部长可以先建空场次，再粘贴 Excel 单列姓名或搜索添加。原名单始终保留；重名要选择具体人员，未匹配项留在输入框继续修正。500 条上限沿用原有保护边界，不代表日常规模要求。
- **培训详情 `/training/:id`**：编辑信息前预览影响人数；编辑同步全部有效考勤。移除撤销本场时长，恢复使用原记录和当前场次信息。冲突时可刷新版本并保留填写。
- **服务标签 `/tags`、`/tags/:id`**：标签组配置、标签维护及具体服务记录关联。分别统计去重人数与有效记录数，解除关联不会删除服务记录。手机详情优先展示记录，可展开分类切换标签。
- **服务记录 `/records/:supportId`**：按当前权限查看一条记录及其标签。姓名链接进入志愿者主页，个人记录上的标签也能直达详情。
- **个人中心 `/me`**：原有服务提交入口选择适用标签，与记录一并保存；点击服务分布图查看记录。修改服务项时明确处理不适用标签，保存后刷新服务分布。受训记录只读，管理人员可进入培训场次维护。个人中心按页读取完整记录，避免原先只取前 50 条导致总时长与历史不完整；待确认、拒绝及已移除记录不计入有效时长。
- 旧 `/projects/*` 页面转到培训入口；旧标签批量写 API 返回 `410`。旧培训标签保留历史详情，迁移后提供新场次链接。

桌面培训页面左侧为场次导航，右侧顶部为紧凑培训摘要，摘要下方是并排的人员录入与当前名单。宽屏内容区最大 1280px，录入与名单各占约半个工作区；粘贴和搜索用选项卡切换，共用底部待加入名单与提交按钮。手机依次展示摘要、录入和名单。视觉沿用网站米白底色、暖棕色标题与圆角卡片，培训采用赭色，服务标签采用青绿色。

## 数据和权限契约

`TrainingSession` 是场次管理来源；`TrainingAttendance` 将场次、志愿者和原有 `ProjectSupport` 一一对应。数据库限制同一场次同一人一条考勤、同一服务记录最多归属一条参加关系，并用复合外键约束三者身份。普通有效服务记录保留原防重索引，场次记录按场次与人员防重，允许同人参加信息恰好相同的不同场次。

创建、编辑、补录、移除和恢复使用事务。场次版本与所有名单写操作一起更新；并发修改会返回可重试的版本冲突，避免重复入账或补录到过期场次信息。业务日期以 `YYYY-MM-DD` 传递，数据库场次日期为 `DATE`。培训时长必须大于 0 且为 0.5 小时倍数。

| 角色 | 场次与名单 | 整场编辑 | 封档 |
|---|---|---|---|
| `admin` | 全局；无需志愿者档案 | 全局 | 沿用更正权限，留审计 |
| `b_admin` | 全局 | 全局 | 不能豁免 |
| `a_admin` | 仅管理当前所属部门的志愿者；人数、校验、搜索和名单一致限域 | 必须覆盖全部有效参加人员 | 不能豁免 |
| `user` | 从个人记录查看自己的考勤 | 不可管理培训 | 沿用本人普通记录规则 |

部长创建的空场次归属创建时的部门；全局管理员或录入员创建的空场次为全局可见，仅全局角色能编辑空场次信息。部长可见全局场次、本部门创建的场次，以及含本部门人员（包括已移除人员）的场次。跨部门场次只显示本部门名单和人数，不允许局部修改整场信息。人员调部门后按当前所属部门管理，保存和恢复再次检查资格及范围。

操作者使用真实 `Account`，受益人使用 `Volunteer`。新增 `submittedByAccountId`、`attachedByAccountId`，原 Volunteer 操作者字段允许为空；不伪造管理员志愿者，也不重写无法辨认的历史归属。序列化、记录显示和导出支持纯管理员姓名。

标签组只由系统管理员配置。普通用户可维护本人记录标签；已获授权的代提交记录也沿用其写权限。部长维护记录始终受当前部门限制。有效与待确认记录均可保存合法标签，统计仅计有效记录。关联、解除、整组选项替换、新建记录和更换服务项都经服务端规则校验；单选替换及记录与标签保存是原子操作。

## 历史配置规则

1. 新配置明确选择 `all`（所有普通志愿服务项）或 `specified`（至少一项）。受训服务项不进入普通标签表单。
2. 旧空范围迁为 `legacy`：继续不出现在提交表单，保留旧手工关联语义，等待管理员明确配置，不突然扩大所有表单的必填要求。
3. 标签、标签组的删除入口采用停用，保留所有历史关联。停用后不能新增关联，重新启用可恢复使用。
4. 修改适用范围、多选改单选及停用不批量改写历史记录；详情标记“需检查”。新的保存严格校验当前规则；同服务项下保留的历史失效标签可明确解除。仍适用的必填组不能解除最后一个合法标签。
5. 更换服务项时必须明确解除或更换不适用标签，记录和标签同时保存。服务项失效在配置中提示，不以同名项目替换。

## 迁移和环境边界

增量迁移：`backend/prisma/migrations/20260922010000_training_sessions/migration.sql`。本地 `postgres / volunteer_tracker` 已应用，Prisma 报告 schema up to date；前端 `http://localhost:3000/training` 和后端 `/api/health` 可访问。

本地开发库在迁移前备份及迁移后盘点（UTC 2026-09-22 01:26:22）中，服务记录为 **0**、受训记录为 **0**，没有需要执行的历史场次映射；此后用户可正常录入新场次，盘点数字不代表持续不变的当前数量。该结果仅描述当前连接的开发数据库，不代表线上约 100 人的平台无历史数据。本次未连接或部署线上环境。升级前完整备份 `/tmp/volunteer-tracker-before-training.dump` 已另行恢复到新建临时 PostgreSQL 容器，恢复成功，台账为 0 条／0 小时，与迁移时盘点一致。

迁移脚本按显式 JSON 清单执行，不将所有 `managed` 标签推断为培训。日期、类型、时长、内容不一致、同人多记录、多重标签和无标签记录先由盘点报告列出；有歧义时保留原数据，人工明确分场后再执行。

从 `backend/` 运行：

```bash
# 只读盘点；可在增量迁移前使用，报告含个人记录 ID，应按备份资料管理。
npm run training:inventory -- /tmp/training-before.json

# 先完成完整 pg_dump 备份与隔离恢复，再执行增量 schema 迁移。
npm run db:migrate:deploy
npm run db:generate

# 默认只预演。ACCOUNT_ID 填真实有效系统管理员的 Account ID。
npm run training:migrate -- --manifest mapping.json --operator ACCOUNT_ID --output /tmp/migration-preview.json
npm run training:migrate -- --manifest mapping.json --operator ACCOUNT_ID --output /tmp/migration-result.json --apply
npm run training:inventory -- /tmp/training-after.json
```

清单格式（`supportIds` 是数据库记录 ID，不是 `PS-…` 展示编号）：

```json
{
  "sessions": [
    {
      "key": "stable-unique-session-key",
      "name": "九月笔译培训",
      "supportIds": ["existing-support-id"],
      "legacyTagId": "optional-whole-tag-id"
    }
  ]
}
```

无标签或混合标签拆分后的场次可省略 `legacyTagId`。提供该字段必须恰好覆盖整标签关联的记录集合。脚本保留服务记录 ID、编号、时长及旧关联，并记录新场次映射审计；同一清单重跑跳过已迁移场次，后续补录、移除、编辑不影响重跑。修改原映射记录集合或原标签会被拒绝。整个清单在一个事务中执行，后续映射失败会回滚前面的写入。

切换其他环境时，先暂停旧应用写入、备份、只读盘点并完成显式映射；隔离演练后迁移 schema 和历史数据，对照报告的 `totals` 按人员／类别／日期／状态验证记录数与时长，再启动新应用。不可仅凭本地空库跳过目标环境核对。无需 reset 或 seed。

回退时保留新 schema、映射和全部新数据；已有新场次后不能直接运行仅理解旧标签的应用。可恢复到隔离数据库排查，修复当前版本后再开放写入。仅在目标环境尚无任何迁移后写入且完整核对过时，才考虑恢复整库备份。
